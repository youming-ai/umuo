# 从 wrangler 迁到 Void：执行手册

给站点负责人照着敲的命令清单，对应迁移方案的 PR 3（staging 验证）、PR 4（关联线上 `umuo-app`）、Workers Builds 改设置与收尾。
**这里的命令都会改 Cloudflare 上的东西，只由负责人在本机执行**；agent 只做到本地构建与 `wrangler deploy --dry-run`。

全部命令都在 `site/` 或 `site/void-staging/` 里跑。Void 1.2.1 要 Node ≥ 24.21，本机默认的 Node 不够，所以 `void` 和带 `voidPlugin` 的 `vite` 一律经 `mise exec node@24 --` 执行
（它只把 Node 24 装进 mise 的缓存，不改全局配置）。

## 0. 先读：几条从 void@1.2.1 源码核实过的事实

| 事实 | 依据（`node_modules/void/` 下） | 对执行的影响 |
| --- | --- | --- |
| 配置文件只认「当前目录/void.config.ts」，没有 `--config` 一类的选项 | `dist/project-paths-*.mjs` 的 `loadVoidConfig(root)`；`dist/cli/cli.mjs` 里 deploy 的参数表只有 `project/dir/spa/skip-build/debug/platform/provision/require-email/atomic`，`root = process.cwd()` | staging 只能放在**另一个目录**：`site/void-staging/`。文档也写了「Use a separate Void project config for each target」（`docs/integrations/cloudflare.md`） |
| 根目录同时有 `void.config.ts` 和 `wrangler.jsonc` 时，构建直接报「Run `void migrate`」 | `dist/cloudflare-config-*.mjs` 的 `materializeCloudflareConfig` | `void-staging/` 里没有 wrangler 配置，不受影响；`site/` 根要到 PR 4 删掉 `wrangler.jsonc` 才能用 Void 构建 |
| **`void migrate` 和 deploy 时的自动迁移，遇到手写的 `void.config.ts` 会直接报错** | `dist/migrate-*.mjs` 的 `migrateLegacyVoidConfig`：已存在且不以 `// Generated by void migrate.` 开头时抛 `void.config.ts already exists. Move the legacy settings into it…` | 方案里「让 `void deploy` 把 `wrangler.jsonc` 吸收进 `void.config.ts`」这条路走不通。PR 4 改为**手写**最终的 `void.config.ts` 并在同一个提交里删掉 `wrangler.jsonc`（见第 2 节） |
| 「关联已有 Worker」的询问只在**不带 `--platform`** 时出现 | `dist/deploy-*.mjs` 的 `maybeLinkCloudflareDeploy`：`options.platform` 有值就直接返回 | staging（新建 Worker）用 `void deploy --platform cloudflare`；PR 4（关联 `umuo-app`）**第一次必须不带 `--platform`**，否则不会按「复用已有 Worker」的流程走 |
| `void secret` 没有 `--platform` 参数，按 `.void/project.json` 里保存的平台走；没存就当作 Void 平台、要求 `void account login` | `dist/cli/cli.mjs` 的 `parseSecretArgs`（只有 `--project`，严格模式）；`dist/secret-*.mjs` 的 `resolveSecretBackend`。只有「关联已有 Worker」流程里的 `saveCloudflareLink` 会写入 `platform: "cloudflare"`，新建 Worker 的 `--platform cloudflare` 部署不写 | staging（新建）上放 secret 用 `wrangler secret put --name umuo-app-void-staging`；PR 4（关联）之后 `void secret` 才可用，仍备一条 wrangler 的只读核对 |
| `routing.headers` 改不掉响应里已有的头 | Void 的 `headerMiddleware` 给 `c.res` 重新赋值，Hono 的 `set res` 会把旧响应的头（除 content-type）抄回新响应（构建产物 `dist/ssr/index.js` 里的 `set res(_res)`） | 我们的中间件回的是 `ASSETS.fetch` 的响应，自带 `Cache-Control`，规则写了也会被覆盖（本地 `wrangler dev` 实测：写了 immutable 规则仍是 `max-age=0`）。所以两份配置都**不写** `routing.headers`，静态资源与现在线上一样是 `public, max-age=0, must-revalidate` |

## 1. PR 3：在独立的 staging Worker 上验证（不碰线上）

`site/void-staging/` 是一个只有三个文件的 Void 项目：

- `void.config.ts`：Worker 名 `umuo-app-void-staging`，绑 `wrangler.jsonc` 里 `previews` 段的预览资源（`NOTIFY_KV` → `269178fa…`，`LICENSES` → `51977029…`，`RELEASES` → `umuo-releases-preview`），
  `WAFFO_ENV=test`，**不写 `routes`**（写了就会把 `umuo.app` 挂到 staging 上）。其余各项与 `site/void.config.ts` 一致，`scripts/void-config.test.ts` 守着。
- `vite.config.ts`：`voidPlugin()`，`publicDir: '../apps/web/dist'`。
- `middleware/01.legacy.ts`：转出 `site/middleware/01.legacy.ts`，路由仍只有 `worker/src/dispatch.ts` 一份。

### 1.1 本地先构建一次（不需要登录）

```bash
cd site && bun install
cd void-staging
mise exec node@24 -- sh -c 'bun --cwd .. run build:web && ../node_modules/.bin/vite build'
cat .void-wrangler.jsonc          # name 是 umuo-app-void-staging，KV/R2 是预览的，没有 routes
grep -o '"assets":{[^}]*}' dist/ssr/wrangler.json
# 期望：{"binding":"ASSETS","not_found_handling":"none","run_worker_first":["/**"],"directory":"../client"}
../node_modules/.bin/wrangler deploy --dry-run --config dist/ssr/wrangler.json --outdir /tmp/umuo-staging-dry
# 期望绑定：NOTIFY_KV 269178fa…、LICENSES 51977029…、RELEASES umuo-releases-preview、ASSETS、5 个 WAFFO_*（WAFFO_ENV="test"）
```

### 1.2 部署 staging

```bash
cd site/void-staging
mise exec node@24 -- ../node_modules/.bin/void deploy --platform cloudflare
```

- 浏览器里登录 Cloudflare，选 umuo 的账号。
- 是新建 Worker，不会问「Link existing Worker」；问到 ISR 选否（配置里已写 `isr: false`，正常不会问）。
- 成功后记下输出里的 workers.dev 地址，下面记作 `$S`：

```bash
export S=https://umuo-app-void-staging.<你的子域>.workers.dev
```

- 部署会在 `void-staging/` 下生成 `.void/`（已 gitignore）与 `void.lock.json`。staging 的 lock 提交与否都可以；提交了，换台机器再部署时不会重新问账号。

### 1.3 八项验证

括号里是本地 `wrangler dev` 跑同一份构建产物时实测的结果，线上应当一致。

**1. 页面与语言**

```bash
curl -sI $S/ -H 'accept-language: ja' | grep -iE '^HTTP|content-language|vary|cache-control'
# HTTP 200，content-language: ja，vary: Cookie, Accept-Language，cache-control: no-cache
curl -sI $S/pricing | grep -iE '^HTTP|content-language'      # 200，content-language: zh-cn
for p in terms privacy activate; do curl -s -o /dev/null -w "/$p %{http_code}\n" $S/$p; done   # 都是 200
curl -sI $S/en/terms | grep -iE '^HTTP|location|set-cookie'
# 301，location: $S/terms，set-cookie: umuo-lang=en; Path=/; Max-Age=31536000; SameSite=Lax
curl -sI $S/en/ | grep -iE '^HTTP|location'                   # 301，location: $S/
```

**2. 404**

```bash
curl -s -o /dev/null -w '%{http_code} %{content_type}\n' $S/no-such-page   # 404 text/html; charset=utf-8
curl -s $S/api/nope                                                         # {"ok":false,"error":"not_found"}
```

**3. 自动更新（最要紧的一项）**：先看空桶，再放文件，再删掉。

```bash
curl -s -o /dev/null -w '%{http_code}\n' $S/download/macos/update.json      # 204（预览桶是空的）
curl -s -o /dev/null -w '%{http_code}\n' $S/download/macos/evil.txt         # 404（不在白名单的文件名）
curl -s -o /dev/null -w '%{http_code}\n' $S/download/macos/umuo-9.9.9-universal.app.tar.gz   # 404（桶里没有）

echo '{"version":"0.0.1","platforms":{}}' > /tmp/update.json
head -c 1024 /dev/urandom > /tmp/umuo-0.0.1-universal.app.tar.gz
bunx wrangler r2 object put umuo-releases-preview/macos/update.json --file /tmp/update.json --remote
bunx wrangler r2 object put umuo-releases-preview/macos/umuo-0.0.1-universal.app.tar.gz --file /tmp/umuo-0.0.1-universal.app.tar.gz --remote

curl -si $S/download/macos/update.json | grep -iE '^HTTP|content-type|cache-control'
# 200，content-type: application/json，cache-control: no-store；body 与 /tmp/update.json 一致
curl -sI $S/download/macos/umuo-0.0.1-universal.app.tar.gz | grep -iE '^HTTP|content-type|content-length|cache-control'
# 200，application/gzip，content-length: 1024，cache-control: public, max-age=31536000, immutable
curl -sI $S/download/macos | grep -iE '^HTTP|location'      # 没有 macos/latest.json 时 503「正在准备中」，与现在的 PR 预览一样

bunx wrangler r2 object delete umuo-releases-preview/macos/update.json --remote
bunx wrangler r2 object delete umuo-releases-preview/macos/umuo-0.0.1-universal.app.tar.gz --remote
curl -s -o /dev/null -w '%{http_code}\n' $S/download/macos/update.json      # 回到 204
```

**4. 探针与限流**

```bash
curl -s $S/api/health                     # {"ok":true,"service":"umuo-app"}（读得到预览 KV）
for i in 1 2 3 4 5 6; do curl -s -o /dev/null -w '%{http_code} ' -X POST $S/api/notify \
  -H 'content-type: application/json' -d '{"email":"staging-test@example.com"}'; done; echo
# 200 200 200 200 200 429
bunx wrangler kv key delete --namespace-id 269178fa91564fc6954a8fd1b33d3be7 --remote 'notify:staging-test@example.com'
```

**5. webhook 验签（`nodejs_compat` 与 `node:crypto`）**

```bash
curl -s -X POST $S/api/waffo/webhook -d '{}'
# 还没设私钥：{"ok":false,"error":"billing_not_configured"}（503）。这一步只说明 Worker 加载成功

cd site
bunx wrangler secret put WAFFO_PRIVATE_KEY --name umuo-app-void-staging   # 粘贴 Waffo **测试环境**的私钥
# 不用 void secret：新建 Worker 的部署不保存平台，void secret 会转去要求登录 Void 平台（见第 0 节）
T=$(($(date +%s)*1000))
curl -s -w ' %{http_code}\n' -X POST $S/api/waffo/webhook -H "x-waffo-signature: t=$T,v1=AAAA" -d '{}'
# {"ok":false,"error":"invalid_signature"} 401 —— 走到了 SDK 的 RSA 验签（node:crypto）并判定不通过
```

伪造的签名只能证明 401 这条路。验签成功（200）要用 Waffo 后台测试模式把 webhook 投到 `$S/api/waffo/webhook`：
响应应是 `{"ok":true…}`，`bunx wrangler kv key list --namespace-id 5197702966104e0a834192959fad8a25 --remote` 里出现对应记录（写进的是预览的 LICENSES）。

**6. 静态资源与缓存头（与线上对照）**

```bash
A=$(curl -s $S/ | grep -o '/assets/[^"]*\.js' | head -1)
curl -sI $S$A | grep -iE '^HTTP|cache-control'
curl -sI https://umuo.app$A | grep -iE '^HTTP|cache-control'
curl -sI $S/fonts/open-sans/open-sans-latin.woff2 | grep -iE '^HTTP|cache-control'
# 三条都是 200，cache-control: public, max-age=0, must-revalidate（与线上一致；见第 0 节为什么不加 immutable）
```

**7. Worker 设置（控制台：Workers & Pages → umuo-app-void-staging → Settings）**

- Bindings：`ASSETS`、`NOTIFY_KV`、`LICENSES`、`RELEASES`（`umuo-releases-preview`）、5 个 `WAFFO_*`；**没有**多出来的 `KV`、`STORAGE`、`DB`、`AI`、`ISR_CACHE`。
- Variables and Secrets：`WAFFO_ENV = test`；secret 只有刚放的 `WAFFO_PRIVATE_KEY`。
- Domains & Routes：只有 workers.dev（和 Preview URLs），**没有 umuo.app**。
- Observability：Logs 开、persist、invocation logs 开；Traces 关。方案里没追清 `invocation_logs` 是否原样传下去，这里就是核对点。
- 命令行补充：`bunx wrangler deployments status --name umuo-app-void-staging`，看得到当前 100% 的 Worker Version。

**8. 请求量**

Void 下 `run_worker_first` 是 `/**`，js、css、字体、favicon 也都进 Worker。在 staging 的 Metrics 里看一次完整打开首页产生几次 Worker 请求，
乘以线上的页面访问量，估算 Workers 请求计费的增量，再决定是否进 PR 4。

**全部通过才进 PR 4。** 任何一项与上面不符（尤其第 3、5 项），按方案第 7 节的底线停在 wrangler。

## 2. PR 4：关联线上 `umuo-app`，第一次用 Void 部署（切换点）

### 2.1 提交前要准备好的代码改动

在一个 PR 里同时做：

1. **删掉 `wrangler.jsonc`**（两份并存时 Void 拒绝构建，自动迁移又不接受手写的 `void.config.ts`，见第 0 节）。删除前把它的内容留在 PR 描述里备查。
2. **把 `site/void.config.ts` 改成下面这样**（就是 staging 那份换成正式资源，再加上域名）。逐项与 `wrangler.jsonc` 对：

```ts
import { defineConfig } from 'void/config'

export default defineConfig({
  inference: {
    appType: 'void',
    build: 'bun run build:web && vite build',
    bindings: { db: false, kv: false, storage: false, ai: false },
  },
  worker: {
    compatibility_date: '2026-07-17',
    compatibility_flags: ['nodejs_compat'],

      WAFFO_PRODUCT_PREMIUM_YEARLY: 'PROD_REDACTED_YEARLY',

  },
  routing: {
    notFound: 'none',
    isr: false,

  cloudflare: {
    name: 'umuo-app',
    // 只有 umuo.app，没有 www（控制台现状）。routes 是整体比对的字段，漏写就会解绑
```

   审查要点：`name` 是 `umuo-app`；KV id 是正式的 `dad4b460…` / `9afc88fe…`（不是预览的 `269178fa…` / `51977029…`）；桶是 `umuo-releases`；

   - `scripts/wrangler-vars.ts`、`scripts/wrangler-vars.test.ts`、`scripts/waffo-setup.ts`：改为读写 `void.config.ts` 的 `worker.vars`（或在 PR 5 前先标注暂不可用）；
   - `package.json` 的 `deploy` / `dev:worker`，`AGENTS.md`、`docs/DEPLOY.md` 里「线上仍是 wrangler deploy」的说法。
4. 本地验证：

### 2.2 部署前检查（在 `main` 还是旧代码时做）

```bash
cd site                      # 这时 wrangler.jsonc 还在
bunx wrangler deployments status --name umuo-app      # 记下当前 100% 的 Version ID，记作 $OLD
bunx wrangler versions list --name umuo-app | tail -20
# 最新一条 Version 必须就是 $OLD。有更新的、未激活的版本（PR 预览上传的）时，Void 可能以 inheritance-source-changed 中止
curl -s -o /dev/null -w '%{http_code}\n' https://umuo.app/download/macos/update.json   # 记下当前是 200 还是 204
curl -s https://umuo.app/download/macos/update.json > /tmp/update-before.json
```

- 控制台确认：Settings → Domains & Routes 只有 `umuo.app`；Preview URLs 开着（Void 的就绪检查要用）。
- **暂停 Workers Builds**（Settings → Build → 断开或停用自动部署），并在切换期间不往 `main` 合并，避免 wrangler 与 Void 交替部署。
  从合并 PR 4 起，到第 3 节第 1 步把 Deploy 命令换掉之前，**Builds 一次都不能跑**（包括手动 Retry）：PR 4 删了 `wrangler.jsonc`，而 Builds 的 Deploy 命令还是 `bunx wrangler deploy`。
  钉死的 wrangler 4.151 在没有配置文件时默认 `--autoconfig`，会做框架探测；`vite.config.ts` 用的是 `voidPlugin` 而不是 `@cloudflare/vite-plugin`，被当成「未配置的 Vite 项目」。
  好的情况是构建失败；坏的情况是自动生成配置，把一个没有 KV/R2 绑定的裸 Vite Worker 部署到 `umuo-app` 上，`/download/macos/update.json` 与 `/api/*` 当场坏掉。
- 选一个不发版的时间窗：发版脚本会在这期间改 R2 里的 `macos/update.json`。

### 2.5 回滚

按顺序，前一步不行再用下一步：

```bash
cd site
mise exec node@24 -- bunx void project rollback $OLD --platform cloudflare   # Void 记录过的版本连同路由一起恢复
bunx wrangler rollback $OLD --name umuo-app -m "回滚 Void 切换"              # 不依赖配置文件；只换代码，路由不动
```
