# 发布门槛实测（PRD §8）

PRD §8 把「快、轻、稳」写成发布门槛。这份文件记录**怎么测的、测出来多少、以及哪几项现在测不了**。

方法比结论重要：下面的数字换一个口径就会得到相反结论（见「内存：口径决定结论」）。

**测试环境**：Apple Silicon (arm64)、macOS 26。被测产物：`bun run build:desktop` 的
**release 构建**（`target/release/umuo-desktop` 与 `target/release/bundle/`）。
不是 debug 构建——门槛针对的是发出去的东西。

---

## 结果

| 门槛 | PRD 要求 | 实测 | 判定 |
| --- | --- | --- | --- |
| **安装包** | ≤ 30 MB | DMG **3.64 MiB**；`.app` **7.76 MiB** | ✅ 余量很大 |
| **空闲内存** | ≤ 80 MB | `phys_footprint` **30 MB**（峰值 35 MB） | ✅ |
| **空闲 CPU** | ≈ 0% | **0.0%**（5 次采样，静置 12 秒后） | ✅ |
| **唤起速度** | ≤ 150 ms | **40 / 103 / 105 / 95 ms**（快捷键按下 → 浮窗出现） | ✅ |
| **首字延迟的客户端额外开销** | ≤ 50 ms | **未测** | ⏸ 见下 |
| **崩溃率** | ≤ 0.2% 会话 | **未测** | ⏸ 见下 |

## 怎么测的

**安装包**：`ls -la target/release/bundle/dmg/*.dmg` 与 `du -sm .../umuo.app`。

**空闲内存**：启动 release 应用 → 静置 12 秒 → `footprint -p <pid>` 取 `phys_footprint`。
**不要用 `ps` 的 RSS** —— 见下。

**空闲 CPU**：静置后 `ps -o %cpu=` 连采 5 次。

**唤起速度**：应用内埋点分两段（`取词耗时` / `唤起耗时`），起点是**全局快捷键处理函数入口**，
终点是 `panel.show()` 返回。用 `osascript` 发真实按键（`keystroke "d" using option down`），
在 TextEdit 里有真实选区的情况下采 4 次。

## 内存：口径决定结论

同一时刻、同一个进程，两种口径差 3.5 倍：

```
ps -o rss=        →  108 MB      （RSS：把 WebKit/AppKit 的共享页也算进本进程）
footprint -p      →   30 MB      （phys_footprint：Activity Monitor 报的就是它）
                                    峰值 35 MB
```

**用 RSS 判会让这一项从"通过"变成"超标 35%"。** macOS 上量应用内存要用
`footprint`（或 Activity Monitor），RSS 会把共同映射的框架页重复计入每个进程。

另有一处口径边界：`footprint -p` 只算**我们这个进程**。WKWebView 的 WebContent 由系统
拉起、不是我们的子进程，没有计入这 30 MB。要把它一起算进去需要按客户端归属去匹配那个进程，
这一步现在没做——所以这里的 30 MB 应当读作「客户端自身进程的空闲占用」。

## 唤起速度：快路径达标，降级路径不达标

分段埋点让两段成本可见：

| 情况 | 取词 | 唤起（含取词） | 说明 |
| --- | --- | --- | --- |
| **Accessibility 读得到**（正常情况） | 33–104 ms | **40–105 ms** | 达标。浮窗本身只占 1–7 ms，成本几乎全在取词 |
| **AX 读不到**（Electron / Java / 远程桌面里的应用） | 540–610 ms | 540–610 ms | **超门槛 3.6 倍** |

降级路径慢是**设计使然**：它要靠模拟 ⌘C + 轮询剪贴板（`CLIPBOARD_POLL_ATTEMPTS`），
必须等复制真的落下来。也就是说：

- 在 AX 可用的应用里，150 ms 门槛**能达到**；
- 在只能走剪贴板的应用里，**达不到**——要达标就得缩短轮询间隔（代价是空转开销）
  或另找一条取词通道。

这条差距之前没人量过，现在记录在案。

## 现在测不了的两项

**首字延迟的客户端额外开销（≤ 50 ms）**：需要一次真实的模型响应才能分离「客户端开销」
与「服务端首字」。本地没有可用的 API Key，而用假端点测出来的只是我们自己写的那个 mock 的延迟。
要测得有：一个真实的 Key，或一个能模拟真实网络时延的本地替身。

**崩溃率（≤ 0.2% 会话）**：需要长期、多会话的真实使用数据。一次冒烟运行说明不了任何事。
要测得有：崩溃上报（PRD §9.6 的服务端不在本仓库）或一段真实使用期。

## 一条测量卫生问题：发布构建会留下一个「抢快捷键」的实例

10:59:40 打包出 `bundle/macos/umuo.app` 的**同一秒**，`/Applications/umuo.app` 出现了
一份二进制完全相同的副本，10:59:57 它被启动并常驻（本次实测已确认并移除）。

**为什么这条要写进实测记录**：全局快捷键同一时刻只能被一个实例持有。
两个实例同时在跑时，**后注册的那个会静默失败**，于是它的埋点一行都不会输出——
测出来的是另一个进程的行为，而报告上看不出任何异常。

所以：测量全局快捷键相关指标前，先 `ps -eo pid=,comm= | grep umuo` 确认只有一个实例。
